# 魔灯多机型汉化工程与发布标准 v1.1

- 制定日期：2026-08-25
- 最后修订：2026-08-31；增加实机验证基线的增量功能包规则，以及模块元数据全文汉化门禁
- 适用范围：Magic Lantern 不同佳能机型、固件版本的简体中文本地化
- 目标：避免汉化引入无法开机、黑屏、崩溃、花屏、功能失效或无法恢复的问题

## 1. 基本原则

1. **汉化是数据适配，不是二进制移植。**
   - 5D3 汉化只能作为翻译语料、术语、字体字符集和实现思路的参考。
   - 禁止把 5D3 的 `autoexec.bin`、地址、链接布局、启动补丁、模块符号表或内存参数直接用于其他机型。
2. **机型与固件版本是不可分割的目标。**
   - `6D 1.1.6`、`5D3 1.2.3` 等必须视为不同平台。
   - 未明确支持的固件版本必须拒绝加载，不能尝试“应该兼容”。
3. **本地化失败必须退回英文，不能影响启动。**
   - 语言文件缺失、损坏、版本错误、内存不足或字体加载失败时，主程序仍必须正常启动。
4. **汉化补丁不得改变相机功能逻辑。**
   - 除文字查找、字体渲染和语言资源加载外，不得顺带修改警告策略、按键行为、启动流程、任务优先级、录像逻辑或模块功能。
   - 必须修改功能逻辑时，应拆成独立补丁、独立测试和独立版本。
5. **编译成功不等于可用，静态校验通过也不等于实机安全。**
   - 公开发布必须经过本文规定的全部发布门禁。

## 2. 5D3 汉化对后续机型的正确用途

### 2.1 可以复用

- 中文术语和表达风格，例如曝光、对焦、录制、叠加显示等统一译法。
- 英文原文到中文译文的映射语料。
- 通用菜单字符串的哈希字典，但必须重新与目标机型英文字符串核对。
- 中文字体的候选字符集合及字体生成方法。
- UTF-8 解码、中文宽度计算和缺字检查的通用测试用例。
- 翻译文件格式、校验器和回退机制。

### 2.2 必须重新验证

- 每个英文字符串在目标机型中是否真实存在。
- 格式化参数是否一致，例如 `%d`、`%s`、`%x`、宽度和精度修饰符。
- 菜单宽度、换行、警告框和帮助页能否容纳中文。
- 目标机型的字体后端、显存格式和屏幕分辨率。
- 主程序可用内存、链接地址、模块符号和启动顺序。
- 目标机型独有功能，例如 6D 的 GPS 菜单。

### 2.3 禁止复用

- 任何绝对地址、ROM 函数地址、`stubs.S`、`consts.h` 和内存补丁参数。
- `RESTARTSTART`、内存池边界和链接脚本结果。
- 5D3 已编译的主程序、模块或符号表。
- 未经核对的机型专属菜单、警告和功能描述。

## 3. 资源架构标准

### 3.1 翻译数据

- 大型翻译表必须作为存储卡外部资源，例如 `ML/FONTS/zh_cn.lng`；不得整体编译进 6D 等内存紧张机型的主镜像。
- 文件必须包含：魔数、格式版本、条目数、偏移、长度和有序哈希表。
- 加载前必须验证：文件最小长度、所有偏移范围、整数溢出、条目数上限、哈希顺序、重复哈希、字符串终止符和 UTF-8 合法性。
- 查找不到翻译时直接显示英文原文。
- 文件损坏、读取失败或分配失败时，只禁用中文，不得终止启动或反复读取。
- 字典必须记录目标英文原文；仅保存“哈希—译文”而无法追溯原文的字典不得作为发布源数据。

### 3.2 字体

- 中文字体必须作为外部资源，不得无预算地嵌入主镜像。
- 字体头、字符映射区、位图偏移区和位图数据区必须全部进行边界校验。
- 所有汉化文本使用的字符必须在构建时执行全量缺字检查。
- 找不到单个字形时应显示占位符或英文，不得越界读取。
- 字体缺失或损坏时，主程序必须以英文字体启动。

### 3.3 内存分配

- 外部语言表和字体的运行时内存占用必须单独统计，不能只统计 `autoexec.bin`。
- 应优先使用一次加载、只读共享；禁止每次菜单刷新重复读取或分配。
- 所有分配必须检查返回值，并提供英文回退路径。
- 必须测试低内存状态、模块全部加载状态以及录像前后的分配行为。

## 4. 目标机型内存安全门禁

每个“机型 + 固件”必须建立一份内存基线：

- `P`：佳能固件受保护内存池的起始边界。
- `E0`：未汉化官方构建的 `.bss` 结束地址。
- `H0 = P - E0`：原版安全余量。
- `E1`：汉化构建的 `.bss` 结束地址。
- `H1 = P - E1`：汉化后安全余量。

构建前必须先按目标平台实际启动代码分类，禁止只按 DIGIC 代际或相近机型猜测：

- **动态 `_bss_end` 型**：启动代码按最终 `_bss_end` 动态划分或检查用户内存；必须对同工具链、同配置的未汉化版和汉化版成对构建，记录增长量 `G = E1 - E0`。
- **固定结束边界型**：启动代码把 Magic Lantern 可用区固定到常量地址；必须从启动源码和最终反汇编双重确认 `P`，再计算绝对余量。
- **固定保留大小型**：启动代码保留固定字节数；必须同时核对装载起点、保留大小和最终结束地址，不能只看 ZIP 或 `autoexec.bin` 文件大小。
- 无法证明属于哪一型时，自动阻止发布；不得借用另一机型的边界或增长上限。

固定边界发布构建必须同时满足：

1. `E1 < P`，不得触碰或越过边界。
2. 默认要求 `H1 >= 16 KiB`。
3. `H1 >= 75% × H0`。
4. 主镜像相对原版增长超过 8 KiB 时，必须给出逐项尺寸解释。
5. 链接脚本或平台内存补丁发生变化时，必须重新建立基线，禁止沿用旧数据。

若上游原版余量本身不足 24 KiB，可使用一次受限例外进入 L1，但必须同时满足：

- `H1 >= 12 KiB` 且 `H1 >= 75% × H0`；
- 最终映射文件证明所有装载段和 `.bss` 均在 `P` 之前；
- 报告显著标为“低余量／仅受控实测”，不得直接进入 L2 或公开分发；
- 至少完成 20 次冷启动和模块逐个加载后，才能重新评估 L2；
- 低于 12 KiB 时没有例外，自动阻止打包。

对于 6D 1.1.6：

- 受保护边界 `P = 0x4E0000`。
- 当前发布校验上限设为 `.bss` 结束地址不高于 `0x4DC000`。
- 曾导致黑屏的 r2 结束地址为 `0x4E0200`，已越界约 512 字节，必须永久列入拒绝清单。

对于 550D 1.0.9：

- 启动代码使用固定结束边界 `P = 0xD00000`，不得用 ZIP 大小或其他机型的增长值代替该边界检查。
- 当前同工具链原版基线为 `E0 = 0xCFB900`、`H0 = 18176` 字节；完整汉化优化构建为 `E1 = 0xCFC500`、`H1 = 15104` 字节，增长 `3072` 字节，保留原版余量的约 `83.1%`。
- 该结果符合 12 KiB 和 75% 的受限例外，但未达到默认 16 KiB 门槛，因此只能标为“低余量／仅受控实测”，不得宣传为已证明完美安全，也不得直接公开发布。
- 不允许通过删除模块、减少译文、删减中文字形、取消缺笔画保护或改变上游 `.hid` 状态换取余量；只能采用不改变功能和显示覆盖的代码精简。
- 升级到 L2 前至少完成 20 次插卡冷启动、20 次关机再启动、逐个加载包内全部模块、递归进入全部子选项，并记录红灯、黑屏、崩溃及模块加载日志；任一异常均退回 L1。

对于使用 `boot-d678` 等动态划分 DryOS 用户内存的机型（例如 6D2 1.1.1）：

- 不得套用 6D 的固定边界；必须用同一工具链分别构建未汉化基线和汉化版。
- 从两份最终 `location.map` 读取 `_bss_end`，计算 `G = E1 - E0`，把它作为启动阶段新增保留内存。
- `G > 8 KiB` 时自动阻止发布；即使 `G <= 8 KiB`，也必须确认启动代码的 `MINIMUM_USER_MEM_LEFT` 检查仍能通过。
- 最优结果是 `G = 0`。主镜像文件变大但因段对齐而未增加 `_bss_end` 时，仍须记录文件增长量及原因。
- 语言表、字体等启动后加载的资源另计运行时内存，不能用 `G = 0` 代替分配失败和低内存测试。

校验器必须从最终 `location.map` 读取地址；不得根据源文件大小或 ZIP 大小推测。

## 5. 翻译内容安全标准

每条翻译必须检查：

- 源英文与目标机型实际字符串完全对应。
- C 格式参数的数量、类型和顺序不变。
- `%%`、换行、制表符和转义字符语义不变。
- 不把用户数据误当作格式字符串。
- 菜单名称、值、右侧状态、帮助文本和警告文本分别测试。
- 译文不过度增长；重要状态值优先采用短译法。
- 不翻译内部文件名、配置键、模块名、脚本 API、符号名和必须保持稳定的标识符。
- 哈希冲突必须导致构建失败，不能静默选用其中一条。
- 目标机型新增字符串必须单独登记，不能假设 5D3 字典已覆盖。
- 每个目标必须扫描该机型最终上游 `autoexec.bin` 中实际编译存在的核心菜单字符串，并与目标平台源码的 `.name`、`.help`、`.help2`、`.choices` 和 `MENU_SET_*` 调用点交叉核对；覆盖率必须为 100%，不能用“公共字典条目很多”代替逐机型证明。
- 核心菜单覆盖报告必须单独列出机型、源码候选数、最终二进制命中数、已翻译数和遗漏数；遗漏不为 0 自动阻止发布。
- 模块汉化必须覆盖模块显示名称、摘要、说明、菜单 `.name`、帮助 `.help`、选择项 `.choices`、右侧状态以及 `MENU_SET_*` 运行时文字；只翻译模块说明不得称为模块汉化完成。
- 模块元数据必须单独扫描已生成的 `module_strings.h` 和最终 `.mo`：`Name`、`Summary`、`Description` 与全部 `Help page*` 均必须有中文结果。不得因模块已列入翻译清单就跳过其 `Description` 或帮助页审计。
- 任一模块详情页仍显示英文长说明、英文模式说明或英文帮助页时，报告必须逐项列出，完整汉化结论为“不通过”；不得以菜单名称已汉化替代模块介绍汉化。
- 汉化范围必须同时包含目标平台当前打包的 `.mo` 模块和被 `.hid` 策略隐藏的模块。隐藏只表示该模块在目标平台不公开显示或不可安全加载，不代表其名称、摘要、详情、菜单和提示文字可以跳过翻译。
- 隐藏模块必须进入与可加载模块相同的源码文字扫描、格式参数检查、字体覆盖和布局审计。若因目标机型缺少符号而不能实机加载，应在报告中标记为“翻译完成、功能未验证”，不得写成“模块可用”，也不得为测试翻译而强行装入发布包。
- 子菜单和子选项必须递归扫描到最深一层，不能只检查模块首页。每个层级的 `.name`、`.help`、`.help2`、`.choices`、当前值、短名称、右侧状态、警告、动态格式串、开关状态文字和运行时生成文字都必须有明确审计结果。
- “子选项已翻译”必须以源代码调用点覆盖率为准，不能用肉眼抽查几个菜单代替；覆盖报告须按模块、菜单层级和文字类型列出已翻译、保持原样、无法静态识别和遗漏四类结果，遗漏数必须为 0。
- 对 `MENU_SET_*` 等先格式化后显示的文字，应在 `snprintf` 前翻译格式串，并逐项证明 `%d`、`%s`、精度和参数顺序完全一致；只对最终动态结果做精确哈希查找不能作为完整覆盖。
- 每个目标包都必须生成模块文字覆盖报告，未翻译、明确保持原样的技术值和无法静态识别的动态文字必须分别列出，禁止只报告字典总条目数。
- 模块列表摘要必须保持单行，并同时检查 UTF-8 字节长度和实际字体像素宽度；`MENU_MAX_HELP_LEN=100` 时正文最多 99 字节，禁止让 `snprintf` 在一个多字节汉字中间截断。
- 模块详情说明必须按目标机型实际字体度量模拟换行；审计须记录左缩进、正文宽度、页脚预留高度、正文需要行数和可用行数。正文未完全消费、静默超出页面或覆盖页脚时自动阻止发布。
- 字库“包含某个码位”不等于屏幕字形完整。必须检查每个字形的宽高、显示宽度、偏移、位图边界、空白位图及边缘裁切；所有实际字号都必须执行缩放后空白字形和笔画连通分量丢失检查。
- 单色中文字库缩小时禁止使用可能跳过整行或整列的单点取样。若源字形的一个非空笔画分量在目标字形中没有任何像素表示，自动阻止发布。
- “文字显示完全”必须同时满足：字符串未被字节缓冲区截断、UTF-8 序列完整、实际像素宽度不越界、自动换行已消费全部正文、最后一行未被页脚覆盖、字形位图未触边裁切、缩放后无整字或笔画消失。任一条件不满足都不能发布。
- 对无法通过静态分析完全证明的显示效果，必须生成固定检查句和实机拍摄清单；“字库有码位”或“模拟图能显示”均不能单独作为最终验收结论。

## 6. 代码变更隔离

汉化分支只允许以下类型的修改：

- 翻译资源生成与加载。
- UTF-8 解码和中文字体渲染。
- 显示层的翻译查找调用。
- 汉化资源打包和校验工具。

发布前必须将汉化源码与同一版本原版源码做差异审计。出现以下变更时自动阻止发布：

- 启动入口、重启代码、ROM 地址或平台桩函数变化。
- 相机功能开关、配置默认值、定时器或任务优先级变化。
- 录像、曝光、存储、供电、GPS 或模块行为变化。
- 与汉化无关的游戏、测试或实验性修改。
- 未解释的二进制段增长。

## 7. 构建与包完整性标准

- 必须从干净的打包目录构建，禁止复用可能缺文件的增量 `build/zip` 目录。
- 构建工具链版本必须记录并固定。
- 运行时显示的 Magic Lantern 版本必须来自汉化所基于的上游安装包名称，不得使用汉化当天的日期替换。例如，以 `magiclantern.2025-06-20.6D.116.zip` 为基线时，界面版本必须是 `2025-06-20.6D.116`。
- 历史包必须固定到与原压缩包对应的历史源码分支/提交（例如 lua_fix、Nightly）；不得用后续机型的当前源码替代。打包仅替换目标 `autoexec.bin`、对应 `.sym`、原包已有的全部 `.mo` 以及新增中文资源，原包条目不得删除。
- **已完成实机验证的基线包，新增实验功能时必须采用增量兼容包。** 默认逐字节保留基线的 `autoexec.bin`、安装文件、原有 `.mo`、原有字体字形和资源；只允许增加明确声明的新模块／资源，以及为新文字补充字形。不得为了加入一个模块而重编译或替换整个核心、全部模块、全局翻译表或既有字形。
- 增量兼容包必须生成“基线 ZIP—候选 ZIP”的逐条目哈希差异报告。除事先声明的文件外，任一新增、删除或字节变化均自动阻止封包；字体变更还必须逐字形证明基线字形位图保持逐字节一致。
- 全量汉化迁移、功能实验和已实测基线修复必须拆为三个独立包与独立测试结论；禁止把它们混入同一次实机测试后称为“原版行为未变”。
- 上游版本、汉化修订号和实际编译时间必须分开记录：
  - 上游版本用于相机界面的固件版本字段；
  - 汉化修订号只用于发布文件名和变更记录，例如 `zh-CN.r4`；
  - 实际编译时间只用于 `Built on`、构建日志和可复现性记录。
- 构建后必须直接检查最终 `autoexec.bin` 中的版本字符串，不能只检查 Makefile 变量或压缩包文件名。
- 禁止伪造上游发布日期、提交 ID 或原作者信息；若无法确认基线来源，构建必须标记为 `UNKNOWN-BASE` 且不得公开发布。
- 最终 ZIP 必须自动检查：
  - `autoexec.bin` 与正确的机型、固件版本匹配；
  - 中文语言文件和字体存在；
  - 字体许可证存在；
  - 模块数量符合预期；
  - 模块未解析符号为零；
  - 无临时文件、旧版文件或其他机型文件；
  - ZIP 可完整解压且每个文件校验值一致。
- 强制资源必须在每次 `zip_contents` 打包时重新复制；不得依赖“打包目录首次创建”规则，否则增量构建可能静默漏掉语言文件或字体。
- 模块发布清单必须区分真实 ELF 模块与策略标记：
  - 非零 `.mo` 才能计入可加载模块，并执行未解析符号检查；
  - 零字节 `.hid` 只是同名模块在菜单中的可见性策略标记，本身不是模块；若同名 `.mo` 同时存在，该 `.mo` 仍是真实可加载候选，必须执行符号审计，不能因隐藏而跳过；
  - 只有 `.hid` 而没有同名 `.mo` 时，只能称为“隐藏策略占位／翻译目录已覆盖”，禁止宣传为“模块可用”；
  - `.mo` 与 `.hid` 的名称集合和字节大小必须与目标机型原包及平台策略逐项核对；
  - 禁止从其他机型复制已编译模块来填充清单。
  - 想把隐藏策略中的模块加入发布包时，必须先用目标机型最终符号表逐个检查未解析符号；存在一个缺失符号即禁止打包。符号全部解析也只代表静态兼容，仍需单模块实机测试。
- 完整汉化包的 `.mo`、`.hid` 名称集合必须与对应上游原包完全一致；不得为了让静态报告变绿而删除隐藏模块、实验模块或存在上游依赖问题的模块，也不得擅自改变其可见性。
- 模块符号审计必须分别计算未汉化上游包和汉化包的“核心符号 + 包内模块导出符号”依赖闭包，并比较未解析符号集合。汉化新增一个未解析符号即自动阻止发布。
- 上游包本来就存在的未解析符号必须保留模块并标记为“上游继承风险／功能未证明”，不能写成汉化导致，也不能声称该模块可独立加载。只有用户明确要求制作独立的 `SAFE-LITE` 变体时才允许删减；该变体不得替代或冒充完整包。
- 不得加入未经该机型验证的提供者模块来凑齐符号；模块清单完整和模块可用性是两项不同结论。
- 包内模块相互提供符号时，报告必须列出依赖关系；符号闭包通过不等于任意单模块都能独立加载，实测必须按实际依赖组合进行。
- 每个发布物必须提供 SHA-256、构建日期、目标机型、目标固件和状态标签。

## 8. 四级验证与发布门禁

### L0：已编译

- 主程序和模块编译、链接成功。
- 仅供开发者分析，不得交给普通用户刷入。

### L1：静态安全候选

- 内存边界、语言文件、字体、格式参数、模块符号和包内容全部通过自动校验。
- 可加载模块与隐藏模块的显示名称、介绍和全部递归子选项均进入覆盖报告，遗漏为 0。
- 摘要单行、详情全文、UTF-8 边界和全部实际字号的字形笔画检查通过。
- 标记 `TEST-ONLY`，只允许受控单机测试。
- 使用 12–16 KiB 固定边界受限例外的构建必须额外标记“低余量”，不得仅凭 L1 结果进入 L2。

### L2：单机实测版

- 在一台匹配机型和固件的相机上完成测试矩阵。
- 连续冷启动不少于 10 次，无黑屏、红灯异常或崩溃。
- 仍不得称为稳定版，只能小范围测试。

### L3：公开测试版

- 至少两台不同机身、两张不同品牌或容量的卡通过测试。
- 累计不少于 50 次启动。
- 核心菜单、录像、回放、实时取景、休眠和模块加载通过。
- 无新增崩溃日志，才可去掉 `TEST-ONLY`。

正式稳定版还应经过更长时间使用和更多测试者反馈；不得只凭一次成功启动升级为稳定版。

## 9. 6D 实机测试矩阵

### 9.1 启动与恢复

- 满电电池、6D 固件 1.1.6。
- 空白卡完整解压安装，冷启动 10 次。
- 菜单打开与关闭、关机重启、取出和重新装入电池。
- 睡眠后唤醒、自动关机后再次启动。
- 删除 `zh_cn.lng` 后确认以英文启动。
- 删除 `zh_cn.bfn` 后确认不黑屏。
- 使用被截断或篡改的语言文件，确认安全回退。
- 删除或改名卡根目录 `autoexec.bin` 后确认原厂系统正常启动。

### 9.2 显示

- 遍历全部主菜单、子菜单、帮助页、警告框和选择框。
- 对包内每个可加载模块逐层进入全部子菜单和子选项，切换每个可选值，检查名称、当前值、帮助、警告和动态状态是否全部汉化；不得只打开模块首页。
- 检查中文缺字、乱码、覆盖、越界、残影和刷新异常。
- 检查超长文本、数字变化、百分比、十六进制值和动态状态。
- 逐个选择模块，拍摄模块列表底部的一行摘要，确认无换行、无右侧截断、无半个 UTF-8 字符。
- 逐个打开模块详情页，确认正文从 10 像素安全边距开始、自动换行后全文可见，最后一行不被作者、许可证和构建信息覆盖。
- 使用包含“一、与、交、修、查”等细横画或分离笔画的固定检查句，在 12、20、23、28、32 像素字号逐项拍照；出现整字消失、横画缺失或笔画粘连即退回 L1。
- 隐藏模块若在目标机型上因符号或功能策略不能安全加载，只执行源码翻译和静态显示审计，并在报告中明确未实测原因；禁止取消 `.hid` 或复制其他机型 `.mo` 来完成显示测试。

### 9.3 相机功能

- 实时取景开关、拍照、录像、回放和删除文件。
- GPS 关闭、内置和外置状态。
- 休眠、省电、温度和电池状态。
- 逐个加载打包模块，并在全部默认模块加载后再次检查内存。
- Arkanoid 等非核心模块不得作为启动依赖。

### 9.4 日志

- 每轮测试后保存 `ML/LOGS`、`CRASH*.LOG` 和其他异常日志。
- 记录相机序列匿名编号、固件版本、卡型号、操作步骤和复现次数。
- 出现一次启动黑屏即停止扩大测试范围，版本退回 L1。

## 10. 灰度发布与回滚

- 新版本先由一名知情测试者验证，再扩大到第二台机身。
- 下载文件名必须包含机型、固件、语言、版本和状态，例如：
  `magiclantern.6D.116.zh-CN.r3-bootfix-TEST-ONLY.zip`。
- 发现启动级故障后必须立即：
  1. 撤下公开下载；
  2. 标记对应 SHA-256 为不安全；
  3. 保留样本用于分析，不再传播；
  4. 发布拔卡启动、移除 `autoexec.bin` 的恢复说明；
  5. 在找到可验证根因前不得只改版本号重新发布。
- 修复包必须解释根因、改动、静态证据、尚未验证的风险和回滚方法。

## 11. 发布前签字清单

只有以下项目全部为“是”，才能进入对应发布等级：

- [ ] 机型和固件版本精确匹配。
- [ ] 基于目标机型原版源码构建，而不是移植其他机型二进制。
- [ ] 汉化差异中没有无关功能改动。
- [ ] 翻译格式参数全部一致。
- [ ] 哈希无重复、无冲突，目标原文可追溯。
- [ ] 中文字体无缺字，字体文件边界合法。
- [ ] 模块摘要的 UTF-8 字节数和实际像素宽度均满足单行边界，没有在多字节字符中间截断。
- [ ] 逐模块详情说明已按实际字体和页脚高度模拟换行，全文可见且缩进、右边距正确。
- [ ] 字体缩放已通过全部实际字号的空白字形、边缘裁切和笔画连通分量检查。
- [ ] 语言或字体文件缺失、损坏时能够回退英文。
- [ ] 最终链接内存满足绝对边界和安全余量要求。
- [ ] 已从目标启动代码确认是动态 `_bss_end`、固定结束边界或固定保留大小，并采用对应校验方法。
- [ ] 运行时语言和字体分配已统计，并测试分配失败。
- [ ] 所有模块依赖符号均有提供者。
- [ ] 汉化包与上游包的模块依赖闭包已成对比较，汉化新增未解析符号为 0；上游继承风险已逐项记录。
- [ ] `.mo` 可加载模块与零字节 `.hid` 策略标记已分开验证；同名 `.mo` 没有因 `.hid` 而漏审。
- [ ] 完整包与目标原包的 `.mo`、`.hid` 清单差异为 0；没有用删模块换取审计通过。
- [ ] 所有隐藏模块均已完成名称、摘要、详情、菜单、帮助、警告和动态文字的汉化审计；未把“翻译完成”误写为“功能可用”。
- [ ] 模块名称、说明、子选项、选择值、帮助、警告和动态格式串已生成逐项覆盖报告。
- [ ] 每个模块的子菜单和子选项已递归扫描至最深层，按调用点统计的翻译遗漏为 0。
- [ ] 所有模块动态格式译文保持格式参数数量、类型、精度和顺序。
- [ ] 所有显示文字均通过字节边界、UTF-8 完整性、像素宽度、正文换行高度、页脚遮挡、字形裁切和缺笔画检查。
- [ ] 从干净目录生成 ZIP，资源完整。
- [ ] 相机界面版本与原始上游压缩包名称一致，汉化日期没有覆盖上游版本。
- [ ] 汉化修订号、上游版本和实际编译时间分别记录。
- [ ] SHA-256 已记录。
- [ ] 已达到声明的实机测试等级。
- [ ] 恢复步骤已经验证。

## 12. 对当前 6D 汉化的结论

- 5D3 汉化数据可以继续作为 6D 的翻译语料基础。
- 不应继续采用“将完整翻译表编译进 6D 主镜像”的实现。
- r2 因越过 6D 内存边界，必须永久禁用。
- r3 已修正已知的主镜像越界并通过静态检查，但在真实 6D 完成测试矩阵之前，仍只能标记为 L1／`TEST-ONLY`。
- 静态校验只能降低风险，不能证明不存在其他硬件相关问题；最终结论必须来自分阶段实机验证和日志。
